# 企业多 Agent 研究报告助手：需求说明

## 1. 项目背景

企业中的产品经理、咨询顾问、运营人员和研究人员，经常需要围绕一个主题收集资料并输出研究报告。

人工完成一份初步研究报告通常需要经历以下过程：

1. 理解研究问题；
2. 将大问题拆分为多个子问题；
3. 搜索多个资料来源；
4. 筛选与问题相关的资料；
5. 根据资料形成分析结论；
6. 检查结论是否有来源支撑；
7. 整理为结构化报告并标注引用。

这个过程耗时较长，而且不同研究人员的资料筛选标准和报告质量可能不一致。

本项目希望构建一个企业多 Agent 研究报告助手：用户输入研究任务后，系统自动规划研究步骤、检索资料、提炼结论、核验证据，并生成带来源的 Markdown 研究报告。

---

## 2. 目标用户

第一版只面向一类用户：研究人员。

研究人员可以是产品经理、业务分析师、咨询顾问、运营人员，或者需要快速完成调研初稿的开发者。

第一版暂时不实现多用户、复杂角色权限和团队协作编辑功能。

---

## 3. 核心业务问题

用户希望快速得到一份研究报告，但不能只得到一段没有依据的大模型回答。

系统输出应当满足：

1. 研究任务被拆分为多个可执行的子任务；
2. 每个子任务都能检索和整理相关资料；
3. 主要结论应当关联具体证据和来源；
4. 系统应当检查结论与证据是否一致；
5. 最终报告应当包含引用来源；
6. 用户能够查看任务当前进度和最终执行轨迹。

系统定位为“有证据的研究初稿生成工具”，不替代领域专家做最终决策。

---

## 4. 用户使用流程

用户提交一个研究任务，例如：

> 分析企业在客户服务场景中使用 AI Agent 的主要价值、风险和落地建议。

系统执行以下流程：

1. 创建研究任务；
2. Planner Agent 将研究主题拆分为多个子任务；
3. Researcher Agent 为每个子任务检索并整理资料；
4. Analyst Agent 根据证据生成分析结论；
5. Reviewer Agent 检查结论是否被证据支撑；
6. 如果证据不足，系统补充研究；
7. Writer Agent 生成带引用的 Markdown 报告；
8. 用户查看报告、引用来源和执行轨迹。

---

## 5. Agent 职责边界

### 5.1 Planner Agent

职责：

- 理解用户研究问题；
- 将问题拆分为 2 到 5 个子任务；
- 为每个子任务定义研究目标和检索方向；
- 输出结构化研究计划。

不负责：

- 直接检索资料；
- 直接得出最终结论；
- 直接生成最终报告。

### 5.2 Researcher Agent

职责：

- 根据一个子任务生成检索查询；
- 检索多个来源；
- 去除重复资料；
- 提取与子任务相关的证据；
- 保存来源地址、标题、发布时间和内容片段。

不负责：

- 编造资料；
- 在没有证据时生成结论；
- 编写最终报告。

### 5.3 Analyst Agent

职责：

- 阅读研究计划和证据；
- 综合证据形成分析结论；
- 为每条结论关联支持它的证据编号；
- 标记证据之间可能存在的冲突。

不负责：

- 修改原始证据；
- 把猜测包装成事实；
- 生成最终格式化报告。

### 5.4 Reviewer Agent

职责：

- 检查每条结论是否有对应证据；
- 检查引用来源是否可信；
- 检查结论是否超出了证据内容；
- 判断是否需要补充研究；
- 输出审核结果和修改建议。

不负责：

- 直接改写最终报告；
- 无限触发返工。

### 5.5 Writer Agent

职责：

- 根据审核通过的结论生成 Markdown 报告；
- 整理报告结构；
- 生成引用列表；
- 标注证据不足或存在争议的内容。

不负责：

- 新增未审核的事实；
- 删除关键风险提示；
- 修改证据原文。

---

## 6. MVP 功能范围

MVP 是 Minimum Viable Product，意思是“最小可用产品”。

它不是随便做一个简化版本，而是用最少的功能验证核心价值是否成立。

第一版 MVP 必须具备：

1. 用户可以创建研究任务；
2. 系统可以生成结构化研究计划；
3. 系统可以执行多个研究子任务；
4. 系统可以保存资料来源和证据；
5. 系统可以根据证据生成结论；
6. 每条主要结论可以关联证据；
7. 系统可以审核结论与证据的一致性；
8. 审核失败时最多补充研究两次；
9. 系统可以生成 Markdown 报告；
10. 用户可以查询任务状态、报告和执行轨迹；
11. 系统可以记录每个阶段的耗时、Token 使用量和预估成本；
12. 长任务可以在后台执行，并支持失败重试和超时控制。

---

## 7. 暂不实现的功能

为了保证项目重点聚焦，以下功能不进入第一版 MVP：

1. React 前端；
2. 用户注册和复杂权限系统；
3. PostgreSQL；
4. 多人协作编辑报告；
5. 在线富文本编辑器；
6. 定时自动研究任务；
7. 多租户和计费系统；
8. 云端正式部署；
9. 复杂监控平台；
10. 多模态图片、PDF 和表格分析。

这些能力会在 MVP 稳定后按需要逐步增加。

---

## 8. 任务状态

一个研究任务需要经过以下状态：

- PENDING：任务已创建，等待执行；
- PLANNING：正在生成研究计划；
- RESEARCHING：正在检索和整理资料；
- ANALYZING：正在生成分析结论；
- REVIEWING：正在核验证据和结论；
- WRITING：正在生成最终报告；
- COMPLETED：任务和报告已完成；
- FAILED：任务执行失败。

如果 Reviewer 发现证据不足，任务会从 REVIEWING 回到 RESEARCHING，补充研究后再次审核。

为防止无限循环，最多允许补充研究两次。

---

## 9. 非功能需求

除功能外，系统还需要满足以下工程要求：

1. 可追溯：每个结论应当能找到对应证据；
2. 可观察：能够记录任务状态、Agent 耗时、Token 和错误；
3. 可恢复：任务失败后支持重试；
4. 可控制：限制最大子任务数量、最大审核次数和最大 Token 预算；
5. 可测试：核心状态流转、数据结构和审核规则应当有自动化测试；
6. 可部署：后续可通过 Docker Compose 一键启动 API、Worker 和 Redis。

---

## 10. MVP 验收标准

当用户提交一个明确的研究任务时，系统应当能够：

1. 返回唯一的 task_id；
2. 生成 2 到 5 个合理的研究子任务；
3. 为每个子任务保存检索到的来源；
4. 生成带 evidence_ids 的结论；
5. 识别缺少证据支撑的结论；
6. 在审核失败时进行有限次数的补充研究；
7. 输出带引用的 Markdown 报告；
8. 查询到任务状态和执行轨迹；
9. 记录每个 Agent 的耗时和 Token 使用量；
10. 在异常情况下保存失败阶段和错误信息。
